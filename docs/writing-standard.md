# Chat Board 清楚技術寫作準則

本準則是 Chat Board 的標準做法。它借用 ASD-STE100（Simplified Technical English，簡化技術英語）的寫作原則，讓討論內容容易理解，並減少歧義。

## 適用範圍與界線

- 適用於技術說明、專案文件、白板筆記、SVG 標籤與圖說，以及使用者操作和錯誤處理說明。
- 使用討論原本的語言。中文借用清楚寫作的原則，不宣稱符合英文 STE 標準。
- 英文若要宣稱符合 ASD-STE100，必須依適用版本的寫作規則、受控詞彙表和專業術語規則逐項檢查；句子簡短或 AI 自述不能作為合規證據。
- 這是作者與 AI 的內容整理規範，不是自動改寫器或合規檢查器。它不改變 HTML 紀錄格式、CLI、唯讀網頁或使用者確認流程。
- 不強制重寫既有紀錄。新增或修訂內容時套用準則，保留原有項目 ID、來源與歷史。

## 寫作原則

### 1. 使用短句，一句處理一個重點

直接寫出主要訊息。把不必要的修飾語和重複說明刪掉。

操作步驟通常每句只放一個動作，並明確表示先後順序。若動作必須同時執行，保留這個關係，不拆成先後步驟。

不要為了縮短句子而刪除必要條件、否定、例外或限制。本專案不對中文套用英文的單字數限制。

### 2. 明確寫出執行者、條件、動作與結果

優先使用直接、主動的句子，例如「AI 更新 HTML」，而不是「HTML 將被更新」。指令若已明確以讀者為執行者，可以直接寫「執行……」。

讀者必須先知道的條件，要放在動作前面。涉及多個元件時，寫出各自的責任。

說明動作完成的依據。不要把「已提出請求」寫成「已完成操作」，也不要用「適當處理」代替實際處置。

若執行者、條件或完成依據未知，標記待釐清，或在 chat session 提問。不要自行補成需求。

### 3. 同一個概念使用同一個名稱

必要的專業術語第一次出現時，先解釋它的意思。後續使用同一個名稱，不為了避免重複而交替使用不同同義詞。

本專案的基本用語如下：

| 用語 | 本專案中的意思 |
| --- | --- |
| 討論紀錄 | 一份自包含 HTML，包含該次討論的白板、項目、圖與歷史。 |
| 白板 | 討論紀錄內的一個顯示頁面，對應 `pages` 中的項目。 |
| 項目 | 問題、想法、筆記、共識、決策或下一步，對應 `items` 中的項目。 |
| 已確認 | 使用者在 chat session 明確同意；不等於內容已驗證正確或工作已完成。 |
| 已完成 | 對應的工作已實際完成；不等於使用者已確認某個方案。 |
| 討論脈絡 | 保留變更前後內容及理由的歷史，對應 `history`。 |

其他專案的術語，以該專案的定義為準。引用時保留來源；需要不同意思時明確區分。

保留程式識別字、CLI 參數、結構欄位、固定 ID、數值和單位。不要為了簡化文字而改名。引述原文時保留原文，另加解釋。

### 4. 分清楚內容的狀態

事實要附上適用的來源或驗證依據。推論與假設要明確標示。提案在使用者確認前，仍然是提案。

共識或決策只有在使用者明確確認後，才能標記 `confirmed: true`，並在更新的 `reason` 記錄確認依據。完成工作則依實際結果記錄，不憑意圖宣稱完成。

這些狀態不取代項目類型。`note` 不一定是已驗證事實；`consensus` 或 `decision` 也可能尚未確認。

簡化文字時保留不確定性。不要把「可能」「建議」「待確認」改成肯定結論。

### 5. 圖與文字使用相同的意思

SVG 標籤使用簡短且一致的名稱。箭頭若有歧義，說明它代表資料流、控制流或步驟順序。

SVG 的字級與尺寸應與白板卡片（標題 16px、內文 14px）保持協調：
- 建議 viewBox 寬度維持在 800 至 1000 之間，並設定相應的 width 與 height 屬性。
- 圖內大標題（若有）：16px 至 18px。若卡片外層已有 `diagram.title`，圖內無須重複放置過大的大標題。
- 區塊與節點標題：14px 至 15px（粗體）。
- 節點內文與資料流說明：12px 至 13px。
- 箭頭標註、微型標籤與補充註解：11px 至 12px。
- 避免在 SVG 內使用過大字級（>20px），以維持圖表與白板筆記、側邊欄決策之間的視覺平衡。

條件或例外放不進圖時，補在圖說或同頁筆記中。不要因圖面空間不足而省略安全限制，或把待議的服務邊界畫成既定架構。

## 寫作例子

含糊的說明：

> 若白板有更新問題，應適當處理後再繼續。

依既有版本衝突規則寫出的具體說明：

> 如果 CLI 回報版本衝突，AI 先重新讀取目前的 HTML。
> AI 整合新內容，並使用剛讀取的版本再次提交更新。
> AI 不得用舊版本的內容強制覆寫新紀錄。

這是中文借用 STE 原則的例子，不是英文 STE 合規範例。改寫時必須先知道實際規則，不能自行增加處置。

## 更新前檢查

作者或 AI 在更新白板與文件前，檢查以下事項：

- 每句的重點清楚嗎？是否有可以刪除的重複說明？
- 執行者、必要條件、動作、順序與完成依據清楚嗎？
- 術語是否一致？必要術語是否已解釋？
- 原意、否定、例外、數值、單位和權限界線是否保留？
- 事實、推論、提案、確認與完成是否分清楚？未知資訊是否仍標記未知？
- 來源、確認理由、項目 ID 和歷史是否保留？圖、圖說與筆記是否一致？

如果缺少會改變意思的重要資訊，先在 chat session 釐清，或保留為待釐清項目。不要只為了讓句子看起來明確就自行填入答案。
